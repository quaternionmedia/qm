| **Task** | Bringing `quaternionmedia/dossier` under the corpus. What the fork procedure got wrong where it was run, what the handoffs asserted that was not true, and the structural fact nobody had written down: every piece of the harness is on one unmerged pull request. |

## 1. The assumption that shaped everything, and it was wrong

The session opened believing what the `/cowork` brief, the handbook, and the
handoff queue all implied: that the corpus has a harness, and that adopting a
project connects that project to it.

`git ls-tree origin/main ci` returns nothing. There is no `ci/` directory on
`main`. No `governance-status.yaml`, no `harness-status.json`, no
`handbook/async-contract.md`, no `handbook/handoffs/` — including the three
dossier pages the session was working from — and nothing in
`project-seed/ide/.claude/commands/`. All of it, 18 commits and +9,151 lines
outside `project-seed/`, is on `evolve/ci-tooling-fixes`, pull request #36,
open and in draft.

The assumption was reasonable and it was invisible, which is the combination
worth naming. Every document the session read described the harness in the
present tense, because every one of those documents is *on the branch that
adds it*. A page cannot tell you it does not exist on `main`. The brief itself
is generated by a tool that only exists there.

This is not a defect in #36. It is what an unmerged branch looks like from
inside itself, and the only reliable defence is the one the discipline record
already names: establish which commit you are talking about before quoting
what it contains. The session did that for dossier, out of habit, and did not
think to do it for the corpus.

**What it changed.** A project branch is cut from `main`, and a project branch
owning unmerged org content is an antipattern this org already has an open
pull request to undo (#25, *"stop this branch owning org content"*). So
`project/dossier` was cut from `main` and dossier adopted a corpus with no
harness in it. The alternative — cutting from the evolve branch to make the
goal look met — would have pinned a downstream submodule to unratified org
state and invented a dependency between dossier and one pull request.

The honest statement is that adoption is complete and the goal is not, and
that one human merge separates them.

**The check that would have caught it:** none existed. The `/cowork` brief
reports the commit you are on and the pull request slots; it does not report
what your *base* contains relative to what you are about to build on. A
project being forked from `main` is a claim about `main`, and nothing asked
the question. That is a plausible addition to `cowork_context.py` — the fork
procedure's step 0 says to confirm which commit you are forking from, and the
brief could answer it for the org side rather than leaving it to a habit.

## 2. Three handoff pages asserted CI that does not exist

`dossier-adoption.md` recorded *"Workflows: `test.yml` and dependabot"*. Both
`dossier-delta-review.md` and `dossier-governance-view.md` warned that dossier's
`🧪 Test` workflow needs Playwright browsers and that their absence locally is
an environment difference rather than a defect.

dossier has no CI. `gh api repos/quaternionmedia/dossier/actions/workflows`
returns exactly one entry, GitHub's dynamic `Dependabot Updates`, which is
generated from repository settings and has no file.
`git ls-tree -r origin/main .github` returns one path,
`copilot-instructions.md`. There is no workflows directory on any ref.

Three pages, written in one afternoon by sessions applying this corpus's own
verification discipline, carried the same false fact — which suggests it was
established once and copied twice rather than checked three times. The
Playwright detail is what makes it convincing: nobody invents a browser
dependency. It is the shape of a fact that was true about a *different*
repository, or inferred from a `uses:` line somewhere, and then propagated.

**What it changed, and in the useful direction.** The correction improves the
work rather than diminishing it. If dossier had a test workflow, the
16-commit delta branch would have had *something* run against it. It has not:
no test, no lint, no review, nothing. That is a stronger argument for the
delta-review handoff than the version the page shipped with.

**The check that would have caught it:** asking the host instead of the
repository. `gh api .../actions/workflows` is one command and it is
authoritative in a way that reading a tree is not — GitHub's dynamic workflows
have no file, so the two methods disagree in both directions. Neither is now
required anywhere; the corrected pages carry both commands inline, which is
weaker than a check and better than prose.

## 3. Two steps of the fork procedure report the wrong answer

Both were found by running it, which is the only way either shows up.

**Its ignore check inverts under `-v`.** The procedure says to run
`git check-ignore -v <paths>` and reads *"exit 1 = nothing swallowed"*. With
`-v`, git prints the matching pattern for **negations** too and exits 0. So a
repository that has correctly applied the procedure's own fix reads as still
broken, and the flag that looks like it adds diagnostic detail is the one that
reverses the verdict. Without `-v`, git lists only genuinely ignored paths and
exit 1 means what the procedure says.

**Its documented fix is inert.** The procedure prescribes a negation per
swallowed path — `!.vscode/settings.json` — under a `.vscode/` exclusion. Git
will not re-include a file whose parent directory is excluded, so that
negation does nothing at all. It changes no behaviour, produces no warning,
and looks exactly right in a diff. The rule has to exclude the directory's
*contents* (`.vscode/*`) for anything below it to have effect.

The session wrote the prescribed fix, re-ran the check, and got the same two
paths back. Both defects surfaced in that one moment, and only because the
verification step was run a second time after the fix rather than treated as
done. The procedure's own words are *"a step is done when its check passes,
not when its command exits zero"* — and the failure mode here was subtler than
that sentence anticipates, because the check itself was reporting the wrong
thing.

**A fourth, and this one the session caused.** `project/dossier` was not
pushed, so the submodule had to be cloned from a path on disk and its `origin`
re-pointed at the canonical remote afterwards. The procedure anticipates
exactly that and says to check the recorded URL — which the session did, and
which is half the job. Re-pointing `origin` does not remove the
remote-tracking refs the local clone created. What was left behind was an
`origin/project/dossier` that GitHub has never heard of, frozen at the commit
the branch held at clone time, with the local branch tracking it. Inside the
submodule, `git status -sb` read `## project/dossier...origin/project/dossier
[ahead 1]` while three commits were unpushed, and `check_pr_base` run there
would have resolved the phantom and measured against the wrong base.

It was found by asking a question `git status` cannot answer — *is there local
state that is not in the working tree?* — rather than by any check. The
procedure now carries the four commands that clear it. The deeper lesson is
that "the URL is canonical" and "this clone tells the truth about the remote"
are different properties, and the first is the one that is easy to verify.

**A fifth, smaller one.** A submodule is a separate clone and does not inherit
`core.symlinks`. On a superproject configured correctly, the seed's own
pointer files *inside* `governance/qm` still materialise as one-line text
stubs on Windows, so copying from them lands a regular file containing the
string `AGENTS.md` where a symlink belongs. The resulting file reads
plausibly. Creating the pointers as symlink objects directly — `git
hash-object -w`, then `git update-index --cacheinfo 120000` — sidesteps the
working tree entirely, and the blob SHAs can then be compared against the
seed's, which is a stronger check than looking at the copy. They matched.

**The check that would have caught them:** the flagless `check-ignore` now in
the procedure, plus a positive control (`git check-ignore .vscode/launch.json`
must still exit 0) so a fix that disables the rule wholesale is distinguishable
from one that carves out two paths. That is now written down. It is prose, not
a gate, and the org has no repository-shaped fixture to run it against.

## 4. A record was drafted stating something the tools then disproved

The adoption record's first draft said `reuse lint` would run in reporting
mode, and its Alternatives section rejected blocking mode on the grounds that
the lint *"would fail on C1"* — the open question of whose name is on the
copyright.

Then the licensing pass was done and `reuse lint` was run. It exits 0. REUSE
verifies that copyright information is *present*, not whose name it carries,
so C1 was never going to make it red. The stated reason was plausible, was
written before the command was run, and was false.

The draft was rewritten in place, which is what a pre-ratification draft is
for. What is worth keeping is the shape of the error: the reasoning was about
what a tool checks, and reasoning about a tool's behaviour is the case the
handoff contract singles out as *"the single most common source of confident
error, and cost under a minute to check"*. It was written in the same session
that had already quoted that sentence.

The corrected disposition is also the stronger one. Reporting mode on a lint
that already passes installs a check that cannot fail — the exact green signal
this corpus keeps finding in its own tooling, and it would have been
introduced deliberately, with a documented justification, by a session trying
to be careful.

## 5. What was built, and how each signal was made to report bad

Four gates now run in dossier. Two were made to fail on purpose before being
believed:

- The **ADR lint** was given a record containing `originally`. It reported the
  file and line and exited 1, then exited 0 once restored.
- **`reuse lint`** was pointed at an identifier with no text in `LICENSES/`.
  It reported the missing licence and the now-unused one, exited 1, then 0.
- The **dependency-licence gate** ships `--selftest`, twelve fixtures of which
  seven must report bad: source-available licences, an absent declaration, and
  an OSI licence outside the allowlist. CI runs the selftest *before* the gate,
  so a run that passes has demonstrated in the same job that it can fail.
- **`submodule-check`** is red, correctly, because *keep everything local* is
  in force and the pinned corpus commit is not on the remote. It is the only
  failing gate and it will go green on the first push.

The gate's normalizer earns its place on evidence rather than doctrine. The
44 installed distributions declare their licences in spellings that disagree —
`MIT` and `MIT License`, `BSD-3-Clause` and `BSD License`, `Apache-2.0` and
`Apache Software License`. A gate comparing raw strings to an allowlist would
have failed honest packages, which is the concrete form of the normalization
requirement the open-license record states abstractly.

The one thing not proven: a `**` default in `REUSE.toml` means no file can
ever be *uncovered*, so that half of the lint cannot report bad by
construction. What remains enforceable is identifier validity and licence-text
presence, which is what the mutation exercised. Worth knowing before treating
a green REUSE check as a statement about coverage.

## 6. Building the view found the failure the corpus keeps describing

The governance view was built afterwards, and it produced one clean instance
of the defect class this corpus has now found seven or eight times: a check
that reports the healthy value because its query returned nothing.

The slot column read `slots.over_limit`. There is no such key. The document
carries `compliant`, `violations` and `exit_status`. The reader found nothing,
`None` is falsy, the `else` branch said `"ok"`, and the table rendered **every
repository in the org as compliant** — including apothecary, which holds three
open pull requests and which the corpus's own dashboard prints as `OVER`.

Nothing failed. No exception, no empty result, no warning. The table was
complete, aligned and confident, and one column of it was fiction.

It was caught by rendering the table beside `harness_dashboard.py`'s output
and noticing the two disagreed. That is not a check; that is having a second
implementation to compare against, which most readers of a dashboard do not.
The check that exists now is a test asserting that a *missing* `compliant` key
yields no answer rather than `ok`, and it was mutation-tested: reinstating the
fallback turns it red.

The general shape is worth stating, because the fix is cheap and the habit is
not. **A reader built against a document schema should be built against the
document**, not against a memory of it — and where a field decides a verdict,
absence must resolve to "no answer" rather than to the benign value. The
`else: state = None` in that function is one line, and it is the difference
between a dashboard and a decoration.

Three further notes from the same build, all smaller:

- A `**` default in `REUSE.toml` means no file can ever be uncovered, so half
  of what `reuse lint` checks cannot report bad by construction. The half that
  can — identifier validity and licence-text presence — is what the mutation
  exercised. Worth knowing before reading a green REUSE check as a statement
  about coverage.
- The TUI's tab loader returns early when no project is selected. A governance
  tab is org-wide, so hung off that path it would have rendered blank forever
  — silently, and blank reads as fine. It is handled before the guard, and a
  test drives the actual app to prove the tab populates with nothing selected.
- A record drafted before its tools were run said `reuse lint` would need
  reporting mode because it would fail on the copyright question. It does not
  check who the holder is. That is §4 above; it belongs here too, because both
  errors are the same error — reasoning about what a tool does instead of
  running it.

## 7. An assertion caught what a diff would not have

While wiring the view into the existing TUI, several edits were applied by a
short Python script run through a shell heredoc. Three of its four anchors
matched; the fourth did not, and the reason was nowhere near the file.

The anchor contained `"\\n"` — the two characters a Python source file needs to
hold a newline escape. The heredoc collapsed the doubled backslash on the way
in, so the script searched for a string containing a *real* newline and
compared it against a file containing a *backslash and an n*. The strings
looked identical in every printed form until they were compared with `repr`
side by side.

What made this a five-minute problem instead of a corrupted file is that the
script asserted every anchor matched exactly once **before writing anything**.
The failed assert aborted the whole script, so the three successful
replacements were discarded too and the file was left untouched. Without that,
three of four edits would have landed, the fourth would have silently done
nothing, and the missing piece would have surfaced later as a widget that
renders empty — which reads as fine.

The reusable part is small and applies to every scripted edit: **assert the
anchor count, and write only at the end.** A scripted edit that replaces what
it finds and shrugs at what it does not is indistinguishable from a successful
one until something downstream is wrong. It is the same failure this whole
corpus keeps naming, arriving through the editor rather than through a check.

## 8. Integrating two stores that must not know about each other

The governance rows and dossier's own `Project` rows describe the same
repositories and cannot be joined by a key. `dossier github sync` empties and
rebuilds the project tables on every run, so a foreign key into them is a
countdown to silent data loss — and the loss would be of governance state,
which is the part nobody would notice was missing.

So the join is made at read time, on names, and never stored. That works, and
it introduces a different problem worth being honest about: a name match can be
wrong. `quaternionmedia/alfred` is an identity; `alfred` is a guess that
happens to be safe inside one organisation and would not be across two.

The resolution was to rank the rules and **render the rule that fired**. A
match on the slug shows as `synced`; anything weaker shows as `synced (name)`,
and the per-project block says "matched to this project by name, not by slug".
The reader sees a link where there is a link and an inference where there is an
inference, which is the same discipline the documents themselves apply to
`unknown` — the value that refuses to pretend it is a measurement.

It is worth noticing that this is the third time in one session the same shape
solved a different problem: unknown carries its reason, a resolved corpus
directory carries why it was chosen, and a name match carries the rule that
made it. In each case the cheap version stores the answer and the honest
version stores the answer *and how it was reached*. The cost is one extra
column or one extra return value. The benefit is that a reader can tell a
finding from a guess without reading the code.

## 9. A read action that writes, chosen deliberately

`governance dashboard` refreshes by default, which means looking at the
dashboard regenerates two committed files in the corpus checkout and leaves a
diff. That is an odd property for something whose name suggests reading, and it
was a deliberate instruction rather than a default anybody drifted into.

The reasoning for it is sound: a dashboard that shows stale figures because
refreshing was a separate command people forget is worse than one that costs
36 seconds and is current. The corpus's own rule — refreshing is a human or
agent action, never CI — is satisfied, because a person ran the command.

What the implementation owes in exchange is that the write is never a surprise.
The command names the directory it is about to regenerate, prints that two
committed files now differ, and says the diff belongs to the reader.
`--no-refresh` is one flag away and is the right choice offline or when only
looking. Whether the default should stay this way after a week of use is worth
revisiting: the honest test is whether anyone has been surprised by a dirty
corpus tree they did not expect.

## 10. What this says about the shape of the work

The conflict table came out at eight rows, and three of them — Textual and
Trogon outside the blessed set, `uv` against the record's named PDM, and the
GitHub API as a single-vendor seam — cannot be closed inside dossier at all.
Two need an org-level record, because the house-stack record deliberately puts
additions at org level so that nobody can relabel a dependency into
compliance.

That is the adoption discipline working. A project that enumerates eight
conflicts is more governed than one that enumerates none, and the rows that
cannot be closed locally are precisely the ones that would have been silently
resolved by a project inventing a local exception. But it also means adoption
generates org-level work: apothecary already uses `uv` too, so the packaging
question has two instances and one answer owed. The corpus has a revision
trigger for exactly this — *"a second project needs the same definition, which
is evidence the rung is org-level after all"* — and this is it firing on the
house-stack record rather than the phase ladder.

## 11. The uncomfortable one

dossier's working tree held 1,833 uncommitted lines across ten files plus an
untracked `src/dossier/database.py`, dated 2026-01-25 to 2026-02-01, on the
branch a queued handoff asks somebody to review. Nothing in the repository
recorded that they existed. The delta-review page describes the branch as
16 commits and +2,392 and says to re-derive before acting — and re-deriving
the *branch* would not have found them, because they were never committed.

They were committed to a `wip/` branch and left alone rather than judged,
which is the conservative move and not obviously the right one: a review of
`393450f` that ignores newer local work may be a review of a superseded
design. That question was put to the human and the answer was to treat the
whole body as draft.

The general point is that a handoff describes what is pushed, and a
workstation holds what is not. Six sessions running in parallel across six
repositories makes the second category larger than anyone is tracking, and the
async contract's clause about declaring a dirty tree you did not dirty covers
finding one — not the reverse case, where a page confidently describes a
branch whose working tree has moved past it.
