# Handoff — The Disk Tooling, and What It Is Still Blocked On

**Goal.** Keep the workstation off zero free space, with the same separation
every other status tool here uses: a generator that measures, a policy that is
reviewed, views that only render.

**Why it exists.** `C:` repeatedly hit zero during August 2026. The QM stack was
never the cause — it measured 1.9 GB in total. The host was: around 102 GB of
NVIDIA driver update artifacts and a 42 GB Docker VHDX. *Those figures are what
the tooling measured on one machine at one moment; they are not org facts and
nothing here re-derives them.*

*Stamped 2026-08-11, and restamped once `ci/` reached `main`. Corpus `main`;
dossier `main` carries `disk.py` and `disk_store.py`. Re-derive before acting.*

---

## What exists

| Piece | Where | Does |
|---|---|---|
| `ci/disk-policy.yaml` | corpus | The reviewed artifact. Names every target and what it costs to get the bytes back |
| `ci/disk_status.py` | corpus | Measures. The only thing that touches the filesystem |
| `ci/disk_dashboard.py` | corpus | Renders |
| `ci/disk_reclaim.py` | corpus | Acts. Dry run unless `--apply` |
| `dossier disk …` | dossier | `check`, `status`, `load`, `delta`, `reclaim`, `reclaims`, `dashboard`, `cookbook`, plus `/disk/*` and a `tab-disk` |
| `006_disk`, `007_reclaim` | dossier | Migrations, chained after `005_governance` |

Three properties worth not breaking, each already carrying a test:

- **The measurement is machine-scoped in full**, and committed in neither
  repository. Unlike `harness-status.json` there is no committable half, so
  there is no `--no-local` flag — there would be no document left.
- **A delta against an unknown is unknown, not zero.** Composition recomputes
  from endpoints rather than summing, so a run nobody could measure cannot be
  laundered into a total.
- **`claimed` and `freed` are different facts.** What the reclaimer removed and
  what the volume gave back diverge routinely, and the document keeps both.

The costs form a **ratchet** — `refetched`, `rebuilt`, `destructive` — so
permitting an expensive tier permits every cheaper one, and a caller cannot
reach for the destructive tier alone.

## Open, and each needing a decision rather than typing

1. **Nothing is scheduled.** `--check` returns 2, 1 or 0 specifically so a
   scheduled task can drive it, and no such task exists. Between manual runs
   the condition this was built for is unmonitored. Whether the org wants a
   Task Scheduler entry, and on whose machine, is a decision — a scheduled
   reclaimer is a program that deletes things while nobody is watching.

2. **Docker's VHDX cannot be reclaimed by pruning.** Pruning frees space
   *inside* `docker_data.vhdx`; the file only grows. Compaction needs Docker
   stopped, and automating that is deliberately refused. So a large, measured,
   unrecoverable figure is reported every run. Either the policy names it as
   permanently excluded with the reason, or somebody accepts a manual step.

3. **`project_delta`, `delta_link` and `delta_note` exist in `dossier.db` with
   no models and no migration.** They predate this work and now collide with
   the disk tooling's own *delta* vocabulary, and they would show as spurious
   drops in any autogenerated migration diff. They are the tables
   `feature/delta-entity-type` adds models for — so this is the same question
   [`dossier-delta-review.md`](dossier-delta-review.md) asks, arriving from the
   other side. Live, dead, or in progress: the answer decides whether a
   migration adopts them or drops them.

4. **The policy is org-level only.** No mechanism lets a project carry its own
   targets. Do not add one without first deciding between copy-forward and
   policy-merge: two policies with no stated merge rule is exactly the drift
   this design avoids, and it would be introduced by the convenience of a
   per-project override.

## Order

Item 3 first — it is the only one that blocks another handoff, and it is a
question about existing data rather than new work. Items 1 and 2 are policy
decisions that can be taken in either order. Item 4 should not be touched until
somebody asks for it; the absence is not a gap. `ci/` reached `main` with #36
on 2026-08-11, so the gate this page used to name first is gone: a project's
next pin bump carries the disk tooling.

## What this does not authorise

Scheduling anything that deletes without a human present. Adding a per-project
policy. Compacting a VHDX automatically. Committing the disk document anywhere
— it is one machine at one moment, and the tool refuses rather than trusting
anyone to remember.
